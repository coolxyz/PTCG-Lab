# 在线对战并发设计与小配置容量验收

日期：2026-10-23。状态：P6-A 已完成基线观测与有界连接池，P6-B 集中推送已完成，P6-C 公平调度已完成，P6-D 常驻 worker 与缓存已完成，P7 容量压测尚未开展；没有实测并发容量结论。本文是[重构设计](产品化重构设计.md)的服务端专项，对应[实施计划](产品化重构分阶段实施.md) P4/P6/P7。

## 1. 要解决的问题

PTCG 是回合制决策游戏，“实时”指操作提交后及时同步，并不要求每秒固定几十次推进规则。玩家思考期间无需运行规则或重复查整局快照。将 GUI、图片和动画留在本地减少静态资源负担，但服务器仍负责所有权威裁定。

同时服务多个对局需要三种保障：状态与权限隔离、有限的性能干扰、可恢复的持久提交。共享 CPU/内存/数据库的单机不能承诺绝对零干扰；超载时应限制新局并保护已开始的局。

研究环境首期实现可作为功能参考，但有以下扩容瓶颈：

| 基线 | 影响 | 目标 |
| --- | --- | --- |
| 一个规则进程加全局执行锁 | 所有局争用一个队列，慢局阻塞其他局 | 按局串行、跨局公平、少量有界 worker |
| LRU 最多 32 局 | 更多活跃局频繁淘汰并完整重放 | 亲和性、内存水位和活跃局准入 |
| 每 WSS 连接约 0.75 秒 auth+snapshot | 玩家不操作也持续查库与组装历史 | 提交触发推送，集中补漏及可控身份复核 |
| 每事务新建数据库连接 | 高连接建立开销 | 小型有界连接池 |
| 常规快照附最近 60 条事件 | 重复读取和传输历史 | 日常只推本次事件，历史按需获取 |
| 每次传输/保存完整私有重放记录 | 长局带来进程间复制和数据库写放大 | 测量后改为初始化记录+追加命令日志，缓存命中只传基线摘要和新命令 |
| 全服务写死 100 并发 | WSS 长连接消耗 HTTP 准入预算 | 分开计算连接、请求、规则队列和数据库预算 |

不要仅增加 Uvicorn 或规则进程数量；每个进程可能重复加载规则和缓存，导致内存耗尽、亲和失效和更多冷恢复。

## 2. 最小部署与资源预算

首期一台机器：一个 API/WSS 进程、一个规则 worker 起步、一个 PostgreSQL；HTTPS 代理按部署环境配置。初期不引入 Redis、Kafka、Kubernetes 或跨机器调度。第二个 worker 仅在 CPU、内存和规则线程安全审计都支持时启用。

以整机 2 vCPU / 2 GiB 为试验条件，建议初始上限：应用容器（含 API 和 worker）1 GiB、PostgreSQL 512 MiB、可选代理约 64 MiB，剩余内存留给系统与文件缓存。它们是待测预算，不是已证明足够的配置；容器、宿主机和压测驱动的消耗分别记录。

连接池从 max=4、短等待队列起步，独立监听/维护连接另计；根据等待指标再调整。数据库 max_connections 需为健康检查、迁移、备份和运维留余量，不能等于所有业务池上限之和。持有 WSS 不持有数据库连接或长期事务。

具体资源/并发参数在 ops 配置中集中声明，并与容量报告绑定。现有 Docker 的默认限额属于旧功能验收配置，不能直接沿用为新产品容量保证。

## 3. 单局顺序与跨局调度

### 3.1 调度器

- 以 matchId 建立串行邮箱，同局最多一条规则计算在执行；进度、认输、控制权变化通过同局协调与数据库版本检查解决竞争。
- 去重键为 `(matchId, authenticatedUserId, commandId)`，同内容在途重试合并等待；不同内容立即冲突。昵称或客户端自报座位不能作为授权依据。
- 全局有界队列，按就绪对局轮转；每局初始可配置一条执行、一条排队，超额返回明确错误。禁止单局长批次持续占用所有计算时间。
- matchId 在存活期间尽量固定到一个 worker。worker 内可以缓存多局，但一次只执行一个引擎动作，避免生成器与全局补丁交错执行。
- 认证、聊天等不存在的未来功能不提前占用规则资源；状态读取和心跳不调度规则执行。
- 目标：冷恢复进入单独的有界任务类别并使用带权公平调度，热命令优先但冷恢复不能永久饥饿。P6-D 先实现独立并发许可证、恢复截止时间和满额可重试拒绝；带权队列纳入 P6-E 收尾，不把限流称为无饥饿调度。单 worker 无法抢占已经执行的恢复任务，只能依靠恢复耗时限制和准入控制。

队列是优化，数据库约束才是最终权威。未来多个 API 实例必须再设计 ownership lease、递增执行代次与 fencing token，当前部署保持一个 API/调度器，不能只改副本数量。

### 3.2 一条命令的提交过程

1. 校验 token、成员、输入尺寸、速率及当前协议；先查询已持久回执。
2. 进入有界单局队列，读取已提交基线（seq、ruleReleaseId、stateDigest、控制权）；这一步结束事务并释放连接。
3. worker 在匹配基线的缓存实例上计算，或从持久记录恢复。随机状态属于该局。
4. worker 返回候选私有记录、摘要和双方独立投影；候选暂不可作为下一命令的有效基线。
5. 短事务按固定顺序锁定对局/成员，再检查状态序号、身份、控制权和规则身份。重复命令返回旧回执，冲突丢弃候选。
6. 原子持久化新状态、双方帧、命令回执、两位接收者的 outbox 记录，成功 commit 后才能向调用方报告 accepted。
7. 将缓存标记为已提交摘要，唤醒推送器。提交失败、超时或结果不明时先查持久回执；未提交候选失效，不能通过内存对象继续推进。

数据库采用按局锁/唯一约束和基线比较，不使用整个大厅或所有对局共用的锁。规则计算、图片访问、WSS 等待和回放下载均不在该事务内。

### 3.3 超时和异常

计算超时先停止对应 worker，并丢弃其所有缓存，不能只取消 Future 后让旧计算继续修改对象。该 worker 的其他局按需恢复；其他 worker 可继续处理。单 worker 模式会出现短暂全局计算暂停，应在容量报告中说明。

超时不等于玩家败北，也不默认新开局或重抽起手。重复引擎失败进入技术暂停/中止诊断，不无限重试消耗整个 CPU。晚到结果必须携带执行代次、基线摘要并被拒绝，防止旧 worker 结果覆盖新的持久状态。

## 4. 缓存、记录与恢复

热缓存键至少包含 ruleReleaseId、matchId 和已提交 stateDigest。不可变卡牌/规则元数据可共享到进程内，但每局实例、随机数、决策候选、状态修改不能共享。

优先保留活跃局；终局立即或短暂展示宽限后释放引擎实例。缓存按实测字节和进程 RSS 控制，不能继续将“32 局”当容量模型。内存达到高水位时停止新局，先释放可恢复的冷局，再决定是否需要降低已允许的并发。

缓存命中时只给 worker 发送必要的命令和基线摘要；未命中再提供恢复数据。持久化的最终目标是初始冻结配置+追加的已接受命令+摘要/结果，避免反复写整份增长的重放 JSON。该存储优化必须有独立 migration、旧格式读取和双向恢复测试；在未完成前保留原格式并如实测量长局成本。

双方的展示帧不是全状态 checkpoint。现有含生成器暂停点的引擎无法直接从任意画面还原；真正 checkpoint 的引入应另行证明随机数、待选项、自动效果和暂停点一致。P6/P7 不依赖它才能完成，允许完整重放，但必须测出冷恢复的限制。

## 5. 推送与断线恢复

### 5.1 事件触发

数据库提交写入接收者明确的 outbox；推送器只读取已提交记录，并再次确认当前连接身份与订阅权限。先投影再推送，同一房间不得广播一份含任一方手牌的快照。

初期由 commit 后的内存通知唤醒，另有一个集中式按游标补漏扫描（建议 1 秒起步，实测调节）。可选 PostgreSQL NOTIFY 只携带非敏感事件 ID/唤醒标记，不携带局面；其事务交付语义见 [PostgreSQL NOTIFY](https://www.postgresql.org/docs/17/sql-notify.html)。通知丢失不影响表中事件，数据库游标才是恢复依据。

不为每个连接启动 0.75 秒数据库轮询。认证到期/撤销仍须执行：新请求校验身份，活动连接按 session 到期调度复核，撤销事件主动断开，并以集中低频校验补漏。

### 5.2 顺序、游标和背压

每位接收者的订阅流包含快照、对局更新、控制权和服务状态。streamCursor 覆盖这些消息；matchSeq 只覆盖持久对局变化。接管操作不能因为 matchSeq 不变而不通知旧页面。

初次快照和游标必须来自一致读取边界。补发从快照之后开始；重复消息由客户端去重。保留期内按游标恢复，游标不存在/超期返回 RESYNC_REQUIRED；跨用户游标直接拒绝。

初期 outbox 保存不可变投影或可定位到对应版本投影的引用。引用所需帧不能提前清理。分发发送成功不等于客户端已处理；保留补发窗口而不是发一次就删除。

每连接按消息字节设队列上限。可合并尚未发送的最新状态，但不能静默丢掉必须确认的控制权/错误/终局信息；无法保留连续序列时明确触发 resync。慢连接超限后关闭并允许恢复，不能阻塞其他玩家。

心跳可从 20—30 秒起步，超时与代理空闲限制协调；客户端指数退避并加抖动。重连风暴应先恢复已存在对局，限制重复身份创建和新的房间初始化。

## 6. 数据库与磁盘预算

复合索引覆盖 `(match_id, seat, seq)` 帧读取、成员授权、命令去重和 outbox 接收者游标。使用 EXPLAIN 与实际读写统计验证，不仅凭添加索引数量判断优化完成。

完整帧可能占用主要存储。首期保留正确帧便于恢复/验收，之后评估压缩、终局归档和只存差异，所有方案都要保持本人视角权限。回放分页并限速，与实时命令分配独立预算。

会话、空房间、outbox 和历史对局分别设置保留策略：outbox 的最小保留窗口覆盖承诺的重连时间；超过窗口可完整重同步。用户仍可访问的回放不能被后台任务无提示删除。清理分小批执行，不锁住全部对局。

持续记录数据库大小、WAL/备份增长、每局平均帧字节和磁盘剩余量。磁盘低水位停止开新局；持久写失败不得响应 accepted。备份演练同时测量对在线延迟的影响。

## 7. 容量模型和指标

令 N 为活跃对局数，r 为每局每秒平均有效操作数，t 为平均规则 CPU 秒数，则规则 CPU 需求近似 `N × r × t`；还要另加投影、序列化、数据库、重放和失败重试成本。连接数、活跃对局数、每秒操作量是三个不同指标。

内存近似为 API 基础占用 + worker 数×规则基础占用 + 热缓存实例 + 数据库与系统预算。公网流量近似为各玩家收到的消息字节之和 + HTTP 重试/重连数据，不把本地卡图流量计入对战 API。网络压缩是否启用需记录，不能假定 HTTP gzip 自动覆盖 WSS。

### 初始目标（待测，不是承诺）

| 指标 | 正常思考负载目标/记录要求 |
| --- | --- |
| 已接受命令丢失、重复执行、跨局串扰或隐藏信息泄漏 | 0；任意一次即失败 |
| 服务端操作延迟 | 从收到有效命令到 commit 并进入推送队列，P95 ≤ 500 ms、P99 ≤ 1.5 s |
| 玩家端可见延迟 | 单独记录网络 RTT、客户端动画排队；不混入服务器处理指标 |
| 热状态重连 | 收到授权订阅到本人快照 P95 ≤ 2 s；不包括离线等待 |
| 长局冷恢复 | 按 100/500/1000 步分别报告分位数，暂不宣称统一 SLA |
| CPU/内存 | 正常稳态 CPU 平均 ≤ 70%，无 OOM/swap 抖动；RSS 稳定并保留运行余量 |
| 超载拒绝 | 有界、明确、可重试；正常目标负载下非预期 5xx/超时比例 < 0.1% |
| 空闲负载 | 不存在按连接周期读取完整状态；统计快照 SQL、认证 SQL、补漏 SQL 各自次数 |
| 公平性 | 记录每局最长排队时间及分布；单局刷请求不能使其他局无限等待 |
| 恢复可靠性 | 提交前/后故障均能核对命令；数据库恢复后的摘要与接受记录一致 |

若达到性能目标但错误被客户端重试隐藏，仍不能算通过。分别报告首次成功率、重试率、拒绝率和用户可见成功率。

## 8. 压测矩阵

压测驱动只扮演两个遵守协议的真人客户端，不导入 H2/A2/LLM，不使用 AI 搜索生成压力。使用原创合成数据验证队列/数据库；真实规则容量测量必须有匹配的合法运行资产。生成器的带宽、CPU 和连接上限不得先成为瓶颈。

| 场景 | 方法 | 检查 |
| --- | --- | --- |
| 空闲连接 | 10/25/50/100 局连接后暂停操作 | CPU、内存、SQL 是否随空闲连接过度增加 |
| 正常思考 | 每局平均 5—15 秒提交一步，加入随机抖动 | 延迟分位数、真实每秒命令数、稳定缓存 |
| 连续操作 | 手牌选择/替补等连续决策无人工等待 | 队列公平性、DB 等待、瞬时峰值 |
| 复杂效果 | 固定可复现的多目标/连锁选择序列 | 最慢裁定是否拖累其他局，投影隐私 |
| 热局与冷局混合 | 超出缓存、轮转访问和长局恢复 | 命中率、重放成本、准入限制 |
| 重连风暴 | 同时断开 25%/50%/100% 客户端后退避重连 | 快照恢复、公平性、CPU 与数据库峰值 |
| 错误与恶意输入 | 越权、旧序号、重复 ID、非法候选、快速猜码 | 不串局、不泄密、限流不误伤全部用户 |
| 慢客户端 | 限速或停止消费 WSS | 每连接队列有界、其他连接不被拖慢 |
| 混合维护 | 回放分页、备份、清理与实时对战并行 | 优先级、锁等待和磁盘开销 |
| 长时间运行 | 在最高达标档位连续至少 2 小时 | 无持续 RSS 增长、outbox 堆积、失效会话积累 |

每档预热 5 分钟、稳态至少 20 分钟，最低重复 3 次并记录随机种子；正确性或资源门槛失败则停止升档，先定位原因。10/25/50/100 是探测阶梯，不是承诺支持 100 局。必要时在失败档与通过档之间细分，发布默认准入低于最高达标值并说明余量。

在同一版本、数据、硬件和配额上做 A/B：轮询对事件推送、新连接对连接池、单/双 worker、不同缓存水位。每次只改变一个变量，不能用更换硬件后的结果宣称代码优化收益。

## 9. 故障注入的硬验收

1. 同局并发相同命令、不同命令、控制权替换及认输：只能接受符合基线的操作，不能重复推进。
2. 两局同 seed、不同 seed，交错执行与独立执行：比较规则摘要、随机结果与各自视角；不得依赖全局 RNG 的执行顺序。
3. 计算完成但事务前杀 worker；事务中断开 DB；commit 后丢 HTTP 响应；commit 后推送前杀 API：分别验证回执核对、缓存失效和 outbox 补发。
4. worker 超时后旧结果晚到、API 重启后旧任务重试：代次/摘要/序号屏障拒绝过时结果。
5. 缓存全清空、单 worker 死亡、规则版本不可用：恢复已提交对局或明确暂停，不重抽种子、不伪造终局。
6. outbox 通知丢失、消息重复/乱序、游标过期：补发或快照恢复；不能导致旧画面覆盖新局面。
7. 撤销 token 后继续使用既有 WSS、另一用户复用游标/房间 ID：拒绝并在规定时间内断开，不泄露成员或私有帧。
8. 隐藏信息金丝雀：给对手手牌、牌库、奖赏和种子植入合成唯一标记，检查 API、WSS、错误和可导出日志均未泄漏。领赏/公开弃牌等合法公开后按事件时间重新判定。
9. 数据库写失败/磁盘不足：不能 accepted 后缺记录；停止新局的同时仍尽力提供已有回放和状态读取。

任一安全或一致性检查失败都阻断阶段验收；“所有玩家最终看到差不多画面”不构成正确性证明。

## 10. 可观测性及结果交付

记录低基数指标：当前房间/对局/连接数、命令率、队列长度/等待、各 op 计算耗时、热缓存命中、重放耗时/步数、DB 池等待、SQL/事务耗时、发送积压、消息字节、outbox 最老未分发时间、进程重启、拒绝和重同步次数。

不把每个 matchId/userId 作为长期指标标签，避免监控自身内存膨胀；按需诊断日志可用去敏关联 ID。令牌、完整候选、手牌、牌库和私有恢复数据不得写入普通观测系统。
