# P5.5 卡组拒绝诊断与 API 兼容方案

本轮 B 的交付基线是现有 API v2：平台逐卡检查已经接入，远端 `INVALID_PAYLOAD` 是最终拒绝，不包含逐卡原因。这一限制必须在产品提示和验收记录中明确。B/C 收尾不要求停止或替换已验收的 API v2 实例；下面是后续服务升级时的协议合同设计，**尚未实现，不是当前服务器能力**。

## 当前产品行为

| 情况 | 产品行为 |
| --- | --- |
| 本地不存在的 printingId、数量、卡池或规则问题 | 用平台本地检查列出 issues、cardRefs 和 suggestions；明确这是本地当前目录检查 |
| 本地通过、远端拒绝 | 显示“服务端未提供逐卡明细”，建议核对服务器规则版本、更新资源或另选版本；不把本地通过等同网络准入 |
| 新版本被明确拒绝 | 清除本次待确认提交，禁止回退使用之前提交的卡组开房；不修改平台原卡组 |
| 超时或结果未知 | 保留 revision、entries、规则和原 requestId；在原身份下恢复，不自动换请求编号 |
| 规则、服务器信任或身份变化 | 不复用旧远端 revision；待确认项必须在原上下文解决 |

上表是 P5.5-B 验收标准；逐卡远端原因不作为本轮已经交付的能力。可继续邀请、开局和双设备验收；新服务升级单独发布、单独回归，不篡改 P4-D/P5 的冻结历史报告。

## 后续增量合同

不直接在旧错误 envelope 添加字段：旧客户端校验严格，未知字段可能变成 INVALID_RESPONSE。也不改变现有提交请求或错误码。建议新服务增加可选的**独立诊断接口** `POST /api/online/v2/decks/validate`，请求仍只含 `protocolVersion`、`ruleReleaseId`、`entries`；不创建 deckRevision、房间或幂等回执，不影响正式提交。

响应独立 schema，包含 `diagnosticVersion: "1"`、`ruleReleaseId`、规范化 `entriesHash`、`valid`、`issues[]` 和 `truncated`。每项 issue 只含稳定枚举 code、可选 printingId、可选 entryIndex；可有经过 schema 限制的数值参数，不传 traceback、Python 类型名、文件路径、任意规则文本或引擎 repr。建议枚举：UNKNOWN_PRINTING、DECK_SIZE、COPY_LIMIT、NO_BASIC_POKEMON、OUT_OF_FORMAT、UNSUPPORTED_EFFECT；规则工作进程异常仍用服务不可用错误，不伪造卡组不合法。不得通过该接口查询其他人的卡组。

校验必须复用正式 submit 的同一 pinned worker 和同一规则入口。上限沿用提交的 entries/body 限制，issue 上限 100、单响应上限 64 KiB，超限置 truncated；为每个身份设置请求速率和并行上限。身份认证、跨 origin 禁止、资源队列预算与正式 API 一致。校验通过只表示检查瞬间的结果，正式 submit 仍须重新裁定。

## 混合版本和发布顺序

1. 服务新增接口；既有 capabilities 和提交/错误 schema 保持字节合同兼容，旧客户端完全不调用新接口。
2. 新客户端先按现有流程提交。明确拒绝后，用户选择“获取服务器诊断”才调用新接口。404/405 表示未支持并保持通用错误；401/403、429、5xx 或断网不能当作支持能力缺失，分别处理认证、限流或临时故障。一次连接可记住“未支持”，重新连接可重新探测。
3. 返回诊断时严格校验 schema、规则和 entriesHash；版本不匹配丢弃，不能把别的卡组原因显示到当前卡组。UI 把本地检查与远端诊断分开，issue 文案由客户端固定映射。
4. 为服务及 native client 发布新包版本和新 API 验收报告。规则行为未变时 ruleReleaseId 保持；如果修正规则，则发布新规则发行版本并保留旧回放。不可只更新冻结摘要以让门禁通过。
5. 最少覆盖新/旧服务 × 新/旧客户端四组合、未知枚举、超限、隐私泄漏、诊断与正式准入等价、服务故障和恶意输入。通过之后再启用产品远端逐卡提示。

此设计将兼容性落到独立端点，避免为了更详细的错误消息破坏正在使用的 v2 客户端。实现与服务升级留在后续 API 功能迭代，本次验收包仍适配当前 v2。
