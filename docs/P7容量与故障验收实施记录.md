## 测试边界

每次创建 `ptcg-p7-` 加随机标识的专属 Compose 项目、内部网络、数据库卷、TLS 和凭据；不加入 LAN 网络、不复用用户数据库、身份或证书。规则只读使用已批准的制品，执行身份必须与镜像匹配；已有服务的配置、镜像、数据卷和进程不作为测试变更目标。

Docker VM 上创建本次专属 cgroup v2 父组，整个 API／规则进程／PostgreSQL 合计硬上限 **2 vCPU／2 GiB，swap=0**。API（含 TLS）1.25 CPU／1 GiB，数据库 0.5 CPU／512 MiB；父组保留 0.25 CPU／512 MiB 余量，不引入未计费的 TLS 代理。子容器 CPU 集限制在测试用核心，生成器使用另一个核心、1 CPU／512 MiB，位于目标资源组之外。

宿主仍是共享的 OrbStack 虚拟机，不将其规格写成物理 2 GiB 整机。本次部署预算、内核计费、生成器与宿主信息分别记录；父组限制包含其后代进程和所计费内核内存。独立资源限制减少争用，不意味着消除了共享存储／宿主环境影响。

测试前记录其他容器的身份、启动时间和健康状态；运行期间只读复核，对原 LAN `/readyz` 做低频检查。保护检查失败、延迟持续异常、目标 OOM／swap 或限额漂移时，仅停止有本次归属标签的压测生成器。故障命令只作用于精确验证标签与项目归属的测试容器；退出时仅删除自己的测试项目、卷和空资源组。

## 工具与计时

`benchmarks/online/lab.py` 管理显式准备、启动、负载、故障与清理；`resources.py` 只允许本次随机命名资源组。测试镜像从已核对摘要的 P6 基础镜像派生，只增加测试观测和负载驱动；构建上下文另设白名单，排除真实规则、卡图、凭据及用户数据。

`observe.py` 不修改生产服务源码、不开放诊断 HTTP 接口；只将固定桶延迟、固定指标、队列计数、连接数和 JSON 载荷字节写入测试卷。命令计时为 **ASGI 收到请求至 HTTP response start**，包括鉴权、排队、计算、持久提交及提交后回执复核，不混称网络 RTT；固定桶分位数为保守上界。JSON 字节不含 TLS／TCP 开销。

`driver.py` 每局创建两个独立原生协议身份，只根据授权投影与合法候选提交操作，不导入产品 AI。优先使用 PassTurn 或合法候选的最小选择，真实规则仍产生全部裁定。每步核对双方序号与视角，最后逐页比对本人全部可见历史；失败保留原 commandId 和私有日志，正常负载不隐藏重试。客户端 HTTP RTT、双方可见耗时、令牌刷新／重连和首次失败单独记录。

思考时间默认为每局 5—15 秒，使用可记录的驱动抖动 seed。真实开局 seed 由服务生成，仅在独立私有记录中保留，不作为驱动决策依据。终局后验证历史并补充新局，记录实际替换数量；短试跑不等价于完整自然终局验收。

为避免同一生成器地址先触发默认每对端限速，试验配置显式提高测试的创建／加入／HTTP／回放额度，保留 HTTP、WSS、计算队列、冷恢复、发送和存储预算；配置进入报告，不能宣称是所有生产默认值下的容量。

## 正式门槛

每档 5 分钟预热、至少 20 分钟稳态、重复至少 3 次，先单 worker 后双 worker；任何正确性错误阻断验收。单档试跑、单次正式样本或只连上 WSS 都不能标记容量通过。最高达标档位至少再运行两小时，并补齐复杂效果、长局冷恢复、重连风暴、慢消费者、混合维护和精确提交边界故障。

基础故障检查先覆盖空闲 worker 死亡、API 重启、专用 DB 暂停与原请求恢复，检查 SQL 回执／帧／序号一致性。该检查不冒充提交中精确杀进程、磁盘不足或满负载故障矩阵；完整项目仍属于 P7-C。

原始输出仅保存在忽略目录 `var/p7/`，包含私有驱动状态，禁止原样导出。公开结果只保留配置、资源、耗时及正确性聚合。P4／P6 历史报告保持原内容。

### 分段诊断

主机 CPU 实测为 Apple M1 Max，Docker VM 仍为 10 个逻辑 CPU／约 15.66 GiB，目标父组为 2 vCPU／2 GiB。新增观测只装配到一次性测试镜像的 app 实例：关联命令的 threadpool 和调度任务，分别记录 SQL 读／写／显式锁、事务提交退出、调度等待、规则计算和事件循环停顿；不保存 SQL 内容、身份或牌面。另记录 API cgroup 限流计数、生成器 CPU／RSS、DB／WAL 增长及实际稳态时长。

受控短对照均为 10 局、30 秒预热＋120 秒稳态，缓存**合计 16**（单 worker 16，双 worker 每个 8），初始规则种子、公开对局 ID、牌组／规则和驱动抖动一致，初始开局指纹核对相同。每组接受 148 步（稳态 113 步），首次失败 0，SQL 序号／回执／双方帧一致，私有回放与可见历史一致。

| 短诊断指标 | 单 worker | 双 worker |
| --- | --- | --- |
| HTTP RTT P95／P99 | 131／140 ms | 354／617 ms |
| ASGI 响应头 P95／P99 保守上界 | 200／200 ms | 400／750 ms |
| 全轮 WAL 同步累计时间 | 10.80 s | 13.72 s |

双 worker 捕获的一条 **760 ms** ASGI 请求中，事务提交退出累计 **709 ms**，规则 worker **7 ms**，调度等待 **0.14 ms**。P7-A 原始累计指标也显示规则命令最大约 43 ms、调度等待最大约 24 ms，而 DB 事务最大约 699 ms。由此定位到持久化提交路径，尚不能把差异归因于双 worker 调度或断言底层存储的最终根因。单独复现时也出现过双 worker HTTP P95 128 ms 的正常轮次，不能选取最快轮次替代原异常。

PostgreSQL 保持 `fsync=on`、`synchronous_commit=on`；额外启用 `track_wal_io_timing`，`wal_sync_time` 是 WAL 同步累计毫秒，含义见 [PostgreSQL 17 官方统计说明](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-WAL-VIEW)。它不是单次提交的 P95，不能用累计平均值代替长尾。一次额外诊断中 DB 运行约 184 s 消耗 8.26 CPU 秒，累计限流约 0.43 s，未见持续 CPU 饱和；与共享 VM 的 WAL／存储等待一起作为后续排查线索。

`waits.py` 的额外等待采样只用于诊断，记录等待类型及计数，正式样本拒绝混入该采样器。第一版把 PostgreSQL 17 的 `WalSync` 大小写写成旧名称，部分事件归入 other；该轮不能作为已直接捕捉 WAL 同步等待的证据，修正标签后另开新数据库确认，未重写旧原始结果。

修正后的确认轮完成 120 秒／2259 次只读查询，捕捉 **115 个 `IO/WalSync`** 活跃后端等待样本、9 个 `LWLock/WALWrite`、10 个 `Lock/transactionid`、1 个 `Lock/advisory`。这是离散采样计数，不是慢请求数或事务分位数；与逐请求 709 ms 提交退出和 WAL 累计同步时间共同支持提交／WAL 同步为当前瓶颈路径，底层 VM／存储抖动的原因仍需在独立部署环境验证。正式矩阵不运行该额外采样器。

原始目录为 `var/p7/b-tail-dual-01/`、`b-tail-paired-w1/`、`b-tail-paired-w1-final/`、`b-tail-paired-w2/`、`b-tail-wal-w2/`、`b-tail-wal-confirm/`。公开受控对照只采用相同运行闭包的 `b-tail-paired-w1-final`／`b-tail-paired-w2`；前两轮工具预检和额外等待观测不拼接成正式矩阵。测试组按轮保存 DB 备份并清理。

### 正式样本执行与判定

`benchmarks/online/matrix.py` 按单 worker 的 10／25／50／100 局，再双 worker 同样各档串行执行；每档三次新数据库重复，300 秒预热、**至少 1200 秒实际稳态**。全套无失败测量最少 10 小时，另计开局、回放核对和备份。正式执行目录为 `var/p7/p7b-matrix-20261027-01/`，私有 `matrix.json` 保存当前样本、逐次结果与停止原因；每个完整样本后更新公开聚合。

同档／重复号使用相同初始开局输入与抖动。终局补局的先后受完成时序影响，因此属于受控初始输入的重复抽样比较，不宣称全时段逐命令严格 A/B。数据库在驱动开始前必须没有对局／回执／帧；结束后比较全部接受命令、SQL 序号总和、回执数和双方帧数，同时验证本人历史。生成器只根据各自授权视角选择合法动作，固定种子不参与其决策。

验收同时检查实际时长、稳态资源采样覆盖、每局持续推进、首次错误、原服务健康／启动身份，以及 P95≤500 ms、P99≤1.5 s、平均 CPU≤2 vCPU 的 70%、无 OOM／swap。生成器平均 CPU 超过其单核 70% 时也不接受样本，以免把生成器瓶颈当服务容量。该检查只证明本次负载的生成器余量，不是生成器最大吞吐测定。

延迟／CPU 不达标时保留该档三次重复，停止该 worker 向更高档递增；另一配置可从 10 局开始。首次通信、一致性或隔离错误立即中止整组，不隐藏重试，也不自动把短诊断改标为正式样本。每个样本完成后先保存备份再清理，只删除本次有归属标记的资源；启动失败也检查归属后清理本次部分资源。

全部结果仍为 `capacityValidated=false`，正式矩阵、复杂效果、长局恢复、两小时稳定性及负载故障尚需各自验收。生产准入和 LAN 配置保持原值。不能通过关闭同步提交、放宽 500 ms 门槛或只报告最快重复来消除长尾。

首个 **10 局／单 worker／第 1 次**正式样本（`m10-w1-r1`）在本次卡牌 ID 热修复开始前，已因提交命令之外的驱动 `ClientError` 自动中止：实际总时长 1064.76 秒，稳态 764.70 秒，未满足 1200 秒；不计作完整正式样本。保护监测通过，测试容器和资源组已清理，原始状态及 PostgreSQL 备份保留。P7-B 仍 in_progress，但当前没有运行中的容量负载；驱动异常原因尚待进一步排查。不得把该失败轮重标为通过。

## P7-B 驱动 ClientError 排查与重启

旧正式首轮仅保存 `ClientError` 类型，未保存错误码和请求阶段；无法从该日志直接还原原异常。已将其数据库备份恢复到新建的内部网络／独立资源组，使用同一私有回放历史复现终局并发校验：串行 10 局全部通过；两轮 10 路并发每轮均为 2 路通过、8 路 `CAPACITY_EXCEEDED / HTTP 503 / retryable=true`；并发为 2 时全部通过。服务端原配置 `REPLAY_INFLIGHT=2`，旧驱动在多局自然终局后直接并发拉取分页回放，没有协调该额度。该触发点与失败时机一致，是已实际重现的失败路径；不把推断写成旧日志已经记录了该错误码。

### 驱动修改与约束

- 全部模拟玩家共享最多两个回放读取名额，只协调每个分页 GET；命令提交不等待该队列、不自动重试。回放 GET 失败同样原样记录并中止，不提高服务器限额、不放宽容量门槛。
- 请求统计按开局、预热、稳态、故障、收尾，以及会话、房间、初始化等待、命令、回放等固定操作分类，记录 attempts／successes／pending／errors 和有界错误码、状态、retryable 账本；不保存 URL、异常消息、token、请求正文或隐藏牌面。
- 初始化任务尚未提升为对局时，已有的 403/FORBIDDEN 轮询单独记入 `initialization_wait.pending`，保留原 60 秒期限。其他 snapshot 403、初始化 503 和到期仍未成功均不能当作正常等待或正式通过。
- 回放队列等待时间独立统计；重复游标／空页仍带后继游标会立即失败，避免验收挂住。收尾校验失败也生成结构化失败结果。
- 正式报告必须覆盖全部请求阶段，没有命令错误不能掩盖终局回放错误。只将明确的初始化等待计入 pending；任何实际请求错误阻断样本。

只在诊断副本中延长了原压测令牌的过期时间，以便在事后重放原私有历史；正式重启仍从全新数据库正常创建身份，不导入旧状态或改动令牌时限。最终新镜像在相同备份上完成串行、两轮 10 路并发及两路并发回放，全部 10/10 通过，保护监测通过；9 项专门回归涵盖并发名额、失败后释放、命令独立性、禁止隐藏重试、游标停滞、日志脱敏、初始化预期等待及永久失败、非命令和收尾阶段失败记录。
