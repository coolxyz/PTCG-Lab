## 测试边界

每次创建 `ptcg-p7-` 加随机标识的专属 Compose 项目、内部网络、数据库卷、TLS 和凭据；不加入 LAN 网络、不复用用户数据库、身份或证书。规则只读使用已批准的制品，执行身份必须与镜像匹配；已有服务的配置、镜像、数据卷和进程不作为测试变更目标。

Docker VM 上创建本次专属 cgroup v2 父组，整个 API／规则进程／PostgreSQL 合计硬上限 **2 vCPU／2 GiB，swap=0**。API（含 TLS）1.25 CPU／1 GiB，数据库 0.5 CPU／512 MiB；父组保留 0.25 CPU／512 MiB 余量，不引入未计费的 TLS 代理。子容器 CPU 集限制在测试用核心，生成器使用另一个核心、1 CPU／512 MiB，位于目标资源组之外。

宿主仍是共享的 OrbStack 虚拟机，不将其规格写成物理 2 GiB 整机。本次部署预算、内核计费、生成器与宿主信息分别记录；父组限制包含其后代进程和所计费内核内存。独立资源限制减少争用，不意味着消除了共享存储／宿主环境影响。

测试前记录其他容器的身份、启动时间和健康状态；运行期间只读复核，对原 LAN `/readyz` 做低频检查。保护检查失败、延迟持续异常、目标 OOM／swap 或限额漂移时，仅停止有本次归属标签的压测生成器。故障命令只作用于精确验证标签与项目归属的测试容器；退出时仅删除自己的测试项目、卷和空资源组。

## 工具与计时

`benchmarks/online/lab.py` 管理显式准备、启动、负载、故障与清理；`resources.py` 只允许本次随机命名资源组。测试镜像从已核对摘要的 P6 基础镜像派生，只增加测试观测和负载驱动；构建上下文另设白名单，排除真实规则、卡图、凭据及用户数据。

`observe.py` 不修改生产服务源码、不开放诊断 HTTP 接口；只将固定桶延迟、固定指标、队列计数、连接数和 JSON 载荷字节写入测试卷。命令计时为 **ASGI 收到请求至 HTTP response start**，包括鉴权、排队、计算、持久提交及提交后回执复核，不混称网络 RTT；固定桶分位数为保守上界。JSON 字节不含 TLS／TCP 开销。

`driver.py` 每局创建两个独立原生协议身份，只根据授权投影与合法候选提交操作，不导入产品 AI。优先使用 PassTurn 或合法候选的最小选择，真实规则仍产生全部裁定。每步核对双方序号与视角，最后逐页比对本人全部可见历史；失败保留原 commandId 和私有日志，正常负载不隐藏重试。客户端 HTTP RTT、双方可见耗时、令牌刷新／重连和首次失败单独记录。

思考时间默认为每局 5—15 秒，使用可记录的驱动抖动 seed。真实开局 seed 由服务生成，仅在独立私有记录中保留，不作为驱动决策依据。终局后验证历史并补充新局，记录实际替换数量；短试跑不等价于完整自然终局验收。

为避免同一生成器地址先触发默认每对端限速，试验配置显式提高测试的创建／加入／HTTP／回放额度，保留 HTTP、WSS、计算队列、冷恢复、发送和存储预算；配置进入报告，不能宣称是所有生产默认值下的容量。

## 正式门槛

每档 5 分钟预热、至少 20 分钟稳态、重复至少 3 次，先单 worker 后双 worker；任何正确性错误阻断验收。单档试跑、单次正式样本或只连上 WSS 都不能标记容量通过。最高达标档位至少再运行两小时，并补齐复杂效果、长局冷恢复、重连风暴、慢消费者、混合维护和精确提交边界故障。

基础故障检查先覆盖空闲 worker 死亡、API 重启、专用 DB 暂停与原请求恢复，检查 SQL 回执／帧／序号一致性。该检查不冒充提交中精确杀进程、磁盘不足或满负载故障矩阵；完整项目仍属于 P7-C。

原始输出仅保存在忽略目录 `var/p7/`，包含私有驱动状态，禁止原样导出。公开结果只保留配置、资源、耗时及正确性聚合。P4／P6 历史报告保持原内容。


## P7-A 首轮结果（2026-10-27）

全部试验使用同一 P6 基础镜像 `sha256:29ad6123c04a878e0d60c000436187adc38fcabadaa9f99ae6916e9eac462d43`；观测镜像与实际驱动／客户端源码摘要另行核对。虚拟机为 OrbStack／aarch64、10 个逻辑 CPU、约 15.66 GiB 内存，目标父组始终严格限制为 2 vCPU／2 GiB，生成器位于另一资源组。没有将虚拟机整体配置成 2 GiB 物理服务器。

每种配置 10 秒预热＋60 秒稳态、10 局／20 客户端。两次均 **73 步接受命令**（稳态 59 步）、首次失败 0，全部本人历史帧与实时可见投影一致；无目标 OOM 或 swap。以下只描述该短负载，不认定任何并发档位达标。

| 指标 | 单 worker | 双 worker |
| --- | --- | --- |
| ASGI 收到请求至响应头 P95／P99 保守桶上界 | 200／200 ms | 750／750 ms |
| 客户端命令 HTTP RTT P95 | 154.9 ms | 614.4 ms |
| 双方均收到可见更新 P95／P99 | 166.2／204.8 ms | 647.6／803.2 ms |
| 目标 cgroup 峰值内存，含其计费缓存／内核，不等于 RSS | 361.0 MiB | 439.7 MiB |
| 采样稳态平均 CPU，占 2 vCPU | 5.94% | 5.76% |

双 worker 的 P95 观测上界高于 500 ms 初始目标，不能宣布目标达标或双 worker 更快。双方虽配额相同，但每 worker 缓存均为 8 个，合计缓存数不同，真实服务开局随机种子也不同；这里只验证工具／功能，不作为严格单变量性能收益对比。P7-B 需补足受控输入、分解排队／恢复／计算耗时及正式重复样本。

另在第三个全新测试组验证 **空闲 worker SIGKILL、API 重启、专用 DB 暂停**；使用原请求查询／重试后，SQL 核对为 **1 局、matchSeq=6、6 条回执、14 个双方帧**。该结果不包含满负载或精确提交边界故障。保护监测未发现原有三个服务重启或失去健康状态。

开始时发现旧 P4-B 宿主输入与容器的 `ruleReleaseId` 不同，服务正确拒绝就绪；复核后使用已批准且与 P6 镜像匹配的制品，只读挂载，没有绕过身份检查。另修正了测试镜像构建引用、数据库首次初始化时序及 internal 网络的就绪探测方式；初次准备失败与首次预试跑保留在私有目录，正式工具证据不拼接为长时矩阵。

聚合报告：[P7-A 隔离及试跑证据](../releases/p7a-isolation.json)。原始结果分别位于 `var/p7/pilot-single-final/`、`var/p7/pilot-dual/`、`var/p7/fault-approved/`，保留受限的 PostgreSQL 自定义格式备份和驱动日志；测量容器、网络、测试卷与空资源组已清理。当前 LAN API／数据库及原 v1 数据库继续运行。报告明确 `capacityValidated=false`、`formalMatrixCompleted=false`、`soakCompleted=false`。

P7 仍 **in_progress**；下一步为 P7-B 正式逐档矩阵，随后 P7-C 长测与完整故障负载。当前没有可发布的最高支持局数或新的生产准入配置。

工具的安全／持续时间／保守分位数／归属保护测试 **16 项通过**，迁移边界、历史报告及公开导出回归 **174 项通过**，合计 **190 项**。发布门禁、协议生成、TypeScript 合同与源码归档、lint 和 diff 检查通过。本阶段未修改生产 API、共享规则或线上客户端源码；P4／P6 验收 JSON 逐字保持历史内容。
