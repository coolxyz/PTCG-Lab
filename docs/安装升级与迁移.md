# 安装升级与迁移

## 通用流程

1. **选定同批交付。** 从可信交付记录核对目标平台、上游卡库提交和制品 SHA-256。桌面另核对预期的活动规则和可对战数量，联网另核对 API 的 `ruleReleaseId` 和 `displayCatalogVersion`。程序版本号可能沿用，需用制品摘要区分具体构建。
2. **保留原资料和回退点。** 保存草稿，确认待处理的联网操作，退出 App 或为服务器安排维护窗口。保留旧程序、原配置和备份截点。桌面备份整个资料目录及另存的外部卡图，网络身份的迁移遵循本文末尾的交接流程。
3. **按平台切换。** 使用下表的入口，保持原用户、资料位置或部署身份。联网规则有变时，协调客户端资料与 API 的切换窗口。先在隔离环境验证同批组合，生产 API 就绪后再开放新规则联网对局。
4. **确认实际生效。** 重开应用或服务，检查实际读取的规则和目录，并验证原资料和身份。桌面用新增卡开一局人机，联网用原身份重连、提交新卡组、开一局并检查本人回放。安装完成、规则启用、实机验收和正式分发分别记录。

| 平台 | 升级入口 | 验收重点 |
| --- | --- | --- |
| macOS Apple Silicon | [DMG 受控安装](#macos-受控安装) | 活动 App 与活动规则、收藏和卡组 |
| Windows x64 | [Setup.exe 原地升级](#windows-x64-原地升级) | 同一 Windows 用户、资料和外观重开、原生 WebView2 与 DPAPI |
| iOS | [TestFlight App 或展示目录更新](#ios-升级) | 同一 Bundle ID 与身份、目录版本、重新冻结及联网开局 |
| API Server | [原 Compose 部署一键更新](#api-server-升级) | 原数据库卷、服务器身份、证书、规则就绪及旧启动命令 |
| 源码 Web | [同批源码与批准运行资产](#源码-web-升级) | 原资料路径、活动同步发布和当前本地规则 |

## macOS 受控安装

1. 完全退出 App，备份 `~/Library/Application Support/org.ptcglab.desktop.preview`。核对 DMG 的 SHA-256，运行介质中的 `Install PTCG Lab.command`。
2. 安装器校验完整 App 的 bundle 摘要，将应用和资料目录作为配套事务备份与切换。保存输出的 `bundleSha256` 和 `transaction`。首次采用已有资料需显式采用，运行中的资料目录会拒绝安装。
3. 打开安装工具给出的活动 App，按下节确认实际对战规则，并核对收藏、卡组和网络身份。

后续含新规则的 DMG 将本机规则升级合并到初始化入口 `Install PTCG Lab.command`。安装成功后，如果已有资料正使用本批支持的旧规则，入口会备份资料并启用新规则。看到规则启用成功后，重开 App 并新建一局人机对战。

维护者也可运行：

```sh
python3 scripts/product/desktop_install.py --root /path/to/install-root --state-dir /path/to/profile status
python3 scripts/product/desktop_install.py --root /path/to/install-root --state-dir /path/to/profile install --candidate '/path/to/PTCG Lab Preview.app' --sha256 TRUSTED_BUNDLE_SHA256
```

`TRUSTED_BUNDLE_SHA256` 是安装工具的 App bundle 摘要，不能用 ZIP 文件摘要替代。已有资料首次采用时增加 `--adopt`。事务中断后先检查 status，再用 `recover --mode finish` 或 `recover --mode abort`；不要手动混合候选文件。回退为 `rollback --transaction TRANSACTION_ID --expected CURRENT_BUNDLE_SHA256`，恢复整套应用和配套状态，不按单局切换旧规则。

### 确认本机对战规则已生效

1. macOS 和 Windows 都在「数据与对战更新」核对「当前发布」，再到「人机对战」核对实际支持数量。将一张本轮新增且已获准的卡加入合法的 60 张卡组，保存版本并开一局。以活动发布和实际开局为准。
2. 已有资料目录的 `app.sync/current.json` 会随安装保留。若它指向资料发布，即使随包卡库已审核，构筑与人机仍可能使用资料发布的卡池。「验证候选对战效果」完成模拟验证，正式发布还要核对完整回归证据。
3. 本机已有同批候选时，退出 App，按该批的交付说明运行规则启用工具。维护者也可在与候选配套且保留完整回归证据的验收源码目录中运行以下命令。示例使用 macOS 的默认路径，Windows 使用对应资料目录和环境的 Python。缺少候选时先走卡库同步流程建立并验收候选。

```sh
PROFILE="$HOME/Library/Application Support/org.ptcglab.desktop.preview"
python3 -B scripts/sync/run.py publish-battle \
  --home "$PROFILE/app.sync" --database "$PROFILE/app.sqlite" --job YOUR_LOCAL_JOB_ID
```

发布前确认批次、活动基线与候选来自当前资料目录。发布后重开 App，重复开局检查。已安装并验收同一上游提交时，无需为启用对战再次执行「同步并适配」。联网对战以所连服务器的能力接口和实际准入为准。 [上游卡库同步流程](上游卡库同步.md)

## Windows x64 原地升级

1. 用原 Windows 用户关闭 App 和已有安装窗口，备份 `%LOCALAPPDATA%\org.ptcglab.desktop.preview`，保留上版整套程序或安装介质。对含原地升级修复的 `Setup.exe` 使用 `Get-FileHash -Algorithm SHA256` 核对交付摘要。
2. 用同一用户运行 Setup.exe。安装器先暂存完整程序，再切换 `%LOCALAPPDATA%\Programs\PTCG Lab Preview`，收藏、卡组、卡图设置及缓存、连接设置、DPAPI 身份和本地对局继续使用原资料目录。新版按资料格式校验兼容性，程序摘要变化不再单独阻止启动。
3. 从开始菜单启动新版，检查原资料、原身份和本机规则。保存一次自定义桌垫或对战外观，重开确认能读回。旧版若将外观存在已失效的临时 WebView 地址中，可能要重新设置一次。
4. 便携方式可选用明确含修复的完整 ZIP，解压到新目录、核对摘要并运行随包 `Verify.ps1`，再从该目录启动 EXE。EXE 与 `backend/` 成套使用。现有资料仍由同一用户读取。

后续含新规则的 Windows 安装包须在安装目录提供 `Update Local Rules.cmd`。安装后，若「数据与对战更新」仍显示旧的活动规则，完全退出 App，以原 Windows 用户双击该命令。看到规则启用成功后重新打开 App，核对「当前发布」，再新建一局人机对战。全新资料直接使用随包规则。

若报 `DESKTOP_INSTALL_REQUIRED`、`DESKTOP_SCHEMA_UNSUPPORTED` 或 `DESKTOP_RECOVERY_REQUIRED`，保留原目录、备份和报错，核对制品与资料格式，按待完成的维护事务处理。需要回退时，使用同一截点的旧整包和配套资料备份。安装器保留的程序目录供安装事务恢复使用，资料回退以升级前的备份为准。

本轮 `b5164fb7` Setup.exe 已交叉构建、解包核验并通过 42 项相关回归。该包未签名，Windows 实机的首次安装、连续升级与回退仍需验证。 [Windows 实机步骤](Windows验证步骤.md)

## iOS 升级

1. 在当前身份下处理待确认的对局命令、大厅操作和会话轮换。通过 App 导出需要保留的收藏和卡组。设备或账号变更时单独安排身份交接，Keychain 和加密日志的恢复范围以已验收的设备为准。
2. 客户端代码或协议有变化时，在同一设备上用同一 Bundle ID 覆盖安装交付记录中可用的 TestFlight 构建。记录版本和 Build，重开后检查收藏、卡组、连接和身份。签名、上传、审核和测试组可用分别核对。 [TestFlight 发布手顺](TestFlight发布.md)
3. 仅展示目录变化且 App 兼容时，在「设置 → 展示资料更新」核对可信 SHA-256，选择 `mobile-display.json`，或从批准的 HTTPS 地址下载。确认预览后应用并重开，核对 `displayCatalogVersion` 与 API 一致。应用前遇到未确认操作，先用原身份恢复。 [单独更新展示目录](iOS开发与验收.md#单独更新展示目录)
4. 在新目录下显式重新冻结卡组，再用原身份联网验证准入、新局和本人回放。展示目录和联网规则各有版本，联网规则由 API 执行。展示包校验失败时继续使用原活动目录。已激活目录异常或 App 版本需要回退时，保留本机资料，按交付方批准的恢复路径处理。

## API Server 升级

1. 选择与服务器架构和原规则版本匹配的一键更新包。安排维护窗口，保留原 Compose 项目、域名、服务器 ID、旧镜像和证书配置。暂停新对局和写入，确认数据库运行且健康。
2. 在原服务器解压并运行 `./update.sh`。原 API 仍在运行时脚本自动识别 Compose 项目。API 已停止或存在多个部署时，传入原 `compose.yaml` 绝对路径及原项目名。脚本停止 API、备份数据库和旧配置、迁移并启动新版。标准离线部署还会更新原安装目录的离线 API 归档及校验清单，原启动命令继续使用。
3. 在原公网入口检查 `/readyz` 和 `/api/online/v2/capabilities`。确认 `acceptingMatches` 已开启，规则 ID 和展示目录与交付清单相符。用原身份重连、提交含新增卡的卡组并开局。用原启动入口重启确认后再恢复流量。
4. 更新失败时保留数据库卷、原身份和备份。按更新包说明重试。若需回退，恢复同一截点的旧镜像归档、清单、配置与数据库。规则变化后的旧局按本人权限提供已保存回放。

[服务器更新、备份和整套回退](API公网部署与自动证书.md#6-更新和整套回退)

## 源码 Web 升级

停止旧进程并备份实际 SQLite、同步目录和独立在线资料目录。在新工作目录准备同批源码与批准运行资产，按使用手册执行 setup 和启动前检查，再沿用已核对的资料路径和在线配置启动。核对活动同步发布、原资料和新增卡人机开局。回退时使用对应旧源码、配套资产及同一截点的资料备份。 [源码安装与启动](启动使用与跨系统迁移.md#从源码安装与启动)

## 网络身份交接

配置服务器与创建/导入身份是分开的动作。关闭 App，用 Mac `scripts/packaging/configure_macos.py` 或 Windows `configure-server.cmd --client-kit PATH` 安装公开连接信息，不复制任何身份。具体 Mac 参数见使用手册。

已有在线身份使用 `ptcg_desktop_api.identity` 的加密 export/import 流程，Windows 可用随包 `identity.cmd`。先查看 `--help`，口令仅在终端隐藏输入，目标必须是新的受保护身份目录。先停止原客户端并备份，不能同时在两台设备继续使用相同身份控制对局。不能直接跨设备复制 Keychain/DPAPI 密文。

身份交接保留服务器身份、未确认命令与恢复记录，仍核对当前规则，不迁移或重标旧规则。卡组可使用界面导出/导入，在线图片缓存和离线展示资源独立管理，详见 [使用手册](启动使用与跨系统迁移.md)。
