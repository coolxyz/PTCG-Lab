## 1. 项目定位和变更授权

PTCG-Lab 是独立于原项目的开源产品，维护资料库、收藏、组牌、人机练习、网络对战和共享规则，不包含 AI 研究、训练、实验调度或研究任务维护。产品内的人机策略和推理属于正常功能，可以直接修改和重构。

过去为了迁移验收而采用的“不改变现有人机练习、保留 AI 任务运行边界、保持旧产品入口不变”不再是 PTCG-Lab 后续开发的永久限制。产品整合可直接调整本仓库的人机界面、控制器、后端编排、启动脚本、资源服务和数据访问层，不需要为了原项目的运行任务另设绕行服务。原项目不是本阶段的部署目标或运行依赖。

仍须保护用户数据、遵守隐藏信息和认证边界、记录规则版本变化，并以回归证明产品行为。已归档的历史规则版本和验收结果不可伪造或原地改写。P5.5-A 要审查迁移期文件冻结门禁：对需要继续演进的产品源码更新门禁作用域及新验收基线，保留历史制品与回放兼容检查；不得仅因旧冻结清单而禁止合理的人机改动，也不得删除检查来掩盖未解释的差异。后续行为调整应有自己的测试与版本记录，不要求所有新行为永远等同旧基线。

## 2. 用户目标和交付边界

用户只启动一个本地 APP 服务，打开同一浏览器地址，即可使用卡牌资料、收藏、我的卡组、人机练习、网络大厅和回放。两种对战都直接选择平台已建立的卡组或保存版本，不再粘贴 JSON、不重复组牌，也不单独启动网络后台或操作网络专用授权 HTML。

远端 API v2 仍单独部署，承担多人裁定、房间和在线持久化。普通玩家启动本地 APP 时不启动服务器或 PostgreSQL。“一个服务”指单一本机 HTTP 监听入口与统一生命周期；必要的规则/人机执行子进程由 APP 管理，不要求用户手工启动，也不另设第二个客户端 HTTP 服务再以反向代理隐藏它。

不在本阶段加入云收藏同步、账号体系、研究训练工具、排位或 P6 的服务器容量优化。Windows 本阶段沿用已验收的 WSL2 后台路径；不把 WSL2 通过写成原生 Windows 凭据后端已支持。

## 3. 现有基础和待补差距

| 现有实现 | 整合工作 |
| --- | --- |
| `apps/web` 完整资料库、收藏、构筑页面；P3-C 已接共享练习界面 | 复用产品壳层，加入正式网络路由及统一卡组选择 |
| `apps/api`、`packages/collection/store`、SQLite 卡组及冻结版本 | 由统一宿主组合，单一数据访问层向两种模式提供卡组快照 |
| `desktop-api` 本机桥接和资源缓存、`online-client` 远端通信 | 作为统一后台内部模块安装，消除专用网络后台启动需求 |
| `desktop-web` PracticeApp、OnlineApp、共享 BattleArena | 通过包公开入口组合，独立模式控制器，共用对战和回放显示 |
| 本地卡图服务与独立网络显示资源清单 | 增加统一资源适配和版本映射，复用平台已有卡图、卡名及缓存 |
| P5 测试包 `start.py` 固定空 manifests、一次性 HTML 授权 | 产品配置支持资源服务，正式入口统一授权；独立测试启动器仅留作诊断 |

目标发布入口由 `apps/desktop-api` 承担统一宿主职责，内部组合现有本地 API 和网络模块；优先通过应用工厂与服务接口复用 `apps/api`，随后逐步收敛旧路径。前端复用 `apps/web` 产品壳层并消费共享包，不复制两份收藏或组牌实现。目录物理迁移可分步完成，但交付时用户只有一个启动命令和一个本地地址。

## 4. 共用卡组及版本合同

1. 复用已有 `/api/decks`、卡组详情及 `/api/decks/{id}/revisions` 语义。可重构其实现，卡组和收藏仍以平台 SQLite 为唯一数据源，网络客户端包不直接打开该数据库。
2. “我的卡组”提供“人机练习”和“网络对战”动作；网络大厅也能选已有卡组。未保存修改须先明确保存或选择已保存版本，不能悄悄拿另一版开局。
3. 开始对战时冻结卡组，形成包含本地 deckId、revisionId、规范化 entries、内容哈希及所选规则标识的只读快照。编辑/删除操作不得改变已开局快照；删除引用版本时保留对局所需内容或明确拒绝删除。
4. 人机适配器读取该快照，网络适配器仅向远端提交协议要求的 `printingId/quantity`、目标 ruleReleaseId 和请求标识。收藏数量、私人备注、本地路径及数据库 ID 不随上传泄漏。
5. 远端 deckRevision 与本地 revisionId 分开保存。映射至少按服务器及信任配置、本机远端身份、ruleReleaseId、规范化内容哈希隔离；保存本地来源版本便于 UI 说明。身份、服务器或规则改变必须重新核对，不能跨域复用 revision。
6. 先展示本地检查，服务器对网络准入作最终裁定。遇到不存在的 printingId、卡池或规则差异，逐条提示用户修正或另选版本，不自动替换卡牌、不修改原卡组。请求结果未知时沿用原幂等 ID 恢复。

人机与网络可以选同一张卡组快照，但不共享当前 matchId、控制权、待确认命令、推进任务或网络游标。

## 5. 共用卡表、卡图和资源

统一宿主提供本地 `CatalogService/CardMedia` 适配接口，资料库、组牌及两种 Arena 从同一资源层获得卡名、文字、卡面和图片。两种模式不各建一份随意更新的完整卡表。

显示资源与裁定规则继续分版本管理。网络模式依据 capabilities 的 displayCatalogVersion 和快照标识解析本地目录；P5 显示接口以 engineId 为主，现有收藏以 printingId 区分卡面，因此需明确 printingId → engineId → 展示资源的映射和同效果多卡面选择规则，不能仅按名称匹配。协议未提供精确卡面身份时采用可说明的默认卡面，不把映射不确定性当作已确认的原卡面。

优先读取平台已有卡图；需要下载时由本机资源模块执行、验证内容哈希并缓存。浏览器只请求本机，API v2 不传卡图或全量显示卡表。不批量上传收藏图片，不把用户图片打入公开安装包。资源缺失或版本不匹配时提示并降级文字，不能阻断合法对战；更新资源时保留在途对局和历史回放所需版本。测试须覆盖真实批准资源，不能只用占位图宣称已接通平台卡图。

## 6. 统一启动、授权和生命周期

- 根启动入口一次创建本机 API、资料/卡组服务、资源服务、人机编排和按需启用的 online-client owner；统一绑定回环地址和明确端口，提供一个 GUI origin。
- 正常进入平台后可直接导航网络大厅。首次授权由统一 APP 启动流程完成，关闭窗口后通过稳定本机地址或启动入口重新进入；不再要求用户寻找临时网络 HTML。重新启动入口时可经受保护的本机机制确认已有实例并打开页面，不能自动终止端口占用者。
- 将既有平台会话与网络窗口授权整合，保留精确 Host/Origin、CSRF/窗口能力及生命周期控制。不能因为旧页面可以公开加载，就让它直接获取远端会话或无限代发操作；不增加免认证的“重新签发授权”HTTP 接口。
- access/refresh token 保存在后台，浏览器不读取；不同服务器和身份隔离。统一 origin 后同步梳理存储键、cookie、静态路径、CSP 和路由冲突。独立 P5 凭据迁入统一 APP 必须显式选择来源、校验权限与服务器身份、避免双 owner；不静默创建新游客冒充原身份恢复。
- 人机计算和同步网络调用不阻塞 HTTP 事件循环；可使用受控任务或执行子进程。此处是产品响应性要求，不是保护原项目 AI 研究任务的约束。
- 在模式间导航不隐式认输、不重复开局、不重复启动人机推进。关闭窗口与退出 APP 分开处理；退出时释放连接、锁和任务，保存待确认记录。网络服务不可用时，收藏、组牌和人机练习仍可使用。

## 7. 分阶段实施和验收

| 工作项 | 交付 | 验收条件 |
| --- | --- | --- |
| P5.5-A 统一宿主和生命周期 | 单后端、单端口、组合应用工厂、统一启动/会话；调整迁移期冻结门禁 | 一条命令启动完整平台；不启动第二个网络 HTTP 服务；重复打开、关闭窗口、后台重启、授权拒绝均可验证 |
| P5.5-B 共用卡组 | 卡组选择器、不可变版本服务、人机和网络适配、远端 revision 映射 | 同一已有卡组可启动两种模式；保存并发冲突、开局后编辑、版本删除、规则/身份切换正确；正常流程不要求 JSON |
| P5.5-C 共用显示资源 | 现有目录和 CardMedia 接入、版本/卡面映射、统一缓存 | 两种模式和资料库正确显示批准资源；断图源后缓存仍可读，缺图降级；远端不出现图片请求或全量卡表传输 |
| P5.5-D 完整产品导航及双设备回归 | 正式网络大厅、共享 Arena/回放、统一恢复入口、发布构建 | Mac + Windows WSL2 各只启动一个 APP，使用已有卡组邀请、自然终局、回放；人机、收藏、构筑及重连回归通过 |

进入本阶段的条件：P5 验收记录明确完成并列明用户确认范围和未逐项报告的限制；先提交 P5 基线，再分项实施。P5.5-D 必须在完整产品入口重做关键双设备流程，不能仅复用独立测试窗口的结果。

补充验收矩阵：

- 全新安装及有用户卡组的升级；数据库备份、迁移失败恢复、历史版本读取。
- 未授权网页、跨站请求、过期窗口、错误服务器、复制标签页和多窗口控制权竞争。
- 同一卡组在人机和网络开局后继续编辑，两个已开局快照保持原内容；网络与人机模式状态不会串用。
- 网络断连、服务器离线、慢规则/人机计算时，本地管理页面仍响应；未知命令先核对回执。
- 桌面和窄窗口、全屏进出、关闭重开、浏览器刷新、APP 重启、历史回放只读。
- 源码和制品扫描、包边界、仓库外安装、授权资源独立供应；安装与启动不依赖原项目目录、数据库、进程或虚拟环境。

每项记录提交/制品版本、资源版本、实际平台和测试结果。源代码冻结检查可以按新的产品边界调整，规则完整性、对手隐私、卡组快照、迁移恢复和实际功能测试继续作为发布门槛。

## 8. 数据升级、回退与后续交接

整合可以改变 PTCG-Lab 的启动方式及人机实现。修改 SQLite 前备份，优先新增表/字段或显式迁移；不能为了统一入口丢弃收藏、卡组、历史对局或网络凭据。涉及执行规则变化时发布新 ruleReleaseId，旧记录按固定版本继续读取/回放或给出明确兼容限制，不修改历史摘要使其看似兼容。

回退以已记录的产品制品和匹配数据备份为单位，具体说明哪些新 schema 能被旧版读取；不能仅换旧前端就宣称完成数据库回退。独立网络诊断启动器可保留，但不是正式用户的必需启动步骤。

P5.5 完成后更新默认路由、根启动文档、组合发布清单和阶段状态，再进入 P6。届时 P6 优化独立 API 的多局调度，P7 测量容量，P8 完成正式打包与运维。当前文档提交不切换运行入口、不启动整合开发，也不把 P5 的 pending 项改为通过。
