## P6-A 起点审计

P6-A 开始时，本仓库每条规则命令启动一次独立子进程，重载规则并重放已提交记录；不是研究环境的常驻 32 局 LRU。WSS 每连接每秒查询一次本人 outbox 并复核认证；每事务原先新建 PostgreSQL 连接，且两条 schema/部署身份校验 SQL 不缓存。容量文档中的研究环境数字不冒充本仓库实测。

先建立观测再优化：数据库连接建立、获取等待、事务（含提交/回滚）及显式 `execute` SQL 次数/耗时；规则进程调用、规则加载、恢复与计算分别计时。指标只保留固定名称的计数、总时长、最大值及固定桶直方图，不保存样本队列、matchId/userId、SQL 文本、凭据或手牌。内部 BEGIN/COMMIT 不计入显式 SQL 数，网络端到端延迟与 IPC 开销不能当成规则 CPU 时间。规则子进程仅返回内部计时，父进程移除后才交给服务，计时不进入持久记录、摘要、回执或 DTO。

## 有界连接池

采用固定版本 `psycopg-pool==3.2.8`，复用现有 `psycopg==3.2.10`。生命周期：API 启动显式 open，min_size=0，按需建立连接；退出时 close，唤醒等待者。构造对象不连接数据库。一次性迁移/脚本 `Repository` 未 open 时仍使用短连接；长期工具通过上下文管理器显式持有并关闭池。

| 环境变量（前缀 `PTCG_ONLINE_V2_`） | 默认值 | 范围 |
| --- | --- | --- |
| DB_POOL_ENABLED | 1 | 0/1；0 使用有界 NullConnectionPool，不复用连接 |
| DB_POOL_SIZE | 4 | 1–32 |
| DB_POOL_WAITERS | 16 | 1–256，禁止 0 代表无限等待者 |
| DB_POOL_TIMEOUT | 1 秒 | 大于 0、不超过 5 秒 |

Compose 对应 `PTCG_V2_DB_POOL_*` 参数。连接池按 API 进程计数；部署仍保持单 API，不增加副本，也不把 max=4 当成整个部署数据库连接总预算。后台维护线程 1 个，额外空闲连接 30 秒后回收。获取池超时/等待队列满映射为现有 `CAPACITY_EXCEEDED`、HTTP 503、retryable=true；数据库故障仍为脱敏 `INTERNAL_ERROR`。不自动重试 SQL 写入；客户端使用原幂等请求恢复未知结果。

每次事务退出前完成提交或回滚，池中空闲连接不持有事务。schema 校验、成员授权、控制权、版本比较、原子回执与 outbox 提交保留。规则计算仍在数据库事务外。失效连接由池淘汰，当前失败请求不会伪装成功。驱动日志滤掉原异常文本，聚合指标保留错误次数。

连接池 API 行为依据 [Psycopg 官方连接池文档](https://www.psycopg.org/psycopg3/docs/api/pool.html)，本地对固定版本执行事务与生命周期回归，不仅依赖最新文档描述。

## 基线与验收方法

`tests/online_v2/test_p6_baseline.py` 在独立 PostgreSQL 上分别使用不复用／复用连接；每种重复 3 次，每次 5 场原创合成对局，每场 20 次双方空闲轮询、4 条有效命令及 4 次原请求重试，核对同样的终局、全部私有帧与隐藏信息隔离。只改变连接复用开关，连接/等待上限相同。未通过 HTTP/WSS 发送链路，也未使用真实规则计算，耗时结果仅衡量该固定服务/SQL 负载。

另用批准规则、固定种子和 5 步操作采集冷加载、恢复、计算指标；每步重新恢复并比较双视角，不导出牌组或恢复记录。完整 P4-D 回归继续包含自然终局、HTTPS/WSS、真实进程死亡、撤销/过期、镜像隔离。保留既有 schema、core/provider/protocol 版本，新增服务版本为 `0.6.0.dev1`。

P6-A 尚未启用认证缓存、集中推送、公平队列、常驻 worker、热缓存或缩小帧等优化，不将 SQL 连接建立减少描述为已经解决空闲轮询成本。旧版本和新版本采用相同数据库 schema，可通过 DB_POOL_ENABLED=0 回退连接复用，或回滚 API 镜像；任何回退都不回退持久化正确性检查。

## P6-B：集中补漏与提交通知

基线提交 `5f1c16f`；新增服务版本 `0.6.0.dev2`，共享 core/provider/protocol、数据库 001—003 migration 和客户端协议均不变。范围限于推送调度；FIFO、公平准入、常驻 worker、缓存和发送字节预算仍在 C/D/E。

### 数据流和权限

- 每个 API 进程持有一个 `StreamHub`，只登记至多 `MAX_STREAMS` 条订阅元数据：内部键、令牌摘要、matchId、已发送游标、错误和一个合并唤醒事件。不保存跨连接快照或消息队列，也不持有数据库连接等待消息。
- 每轮以一个 SQL 查询所有订阅的令牌、会话和本人 `match_members.stream_cursor`；连同原有 schema／部署校验为 3 次显式 SQL。没有订阅时不查库。查询不读取 `matches.recovery`、`match_frames.snapshot` 或 `match_outbox.snapshot`。
- 订阅初次接入始终调用原有 `Matches.stream`；之后仅在游标变化时读取本人的 durable outbox。读取仍在事务内校验当前令牌、成员关系和游标归属，并保留现有锁。快照与游标保持一致；控制权事件即使 matchSeq 不变也会更新收件人游标。
- 批量查询是通知提示，不是授权缓存。访问令牌／会话到期、令牌轮换、撤销及成员不存在都会唤醒连接并返回原有错误。写命令、实际帧读取继续独立执行完整鉴权；数据库不可用时关闭受影响订阅，恢复后按持久游标重连。
- 扫描按每位收件人的最新游标比较，不引入提交前分配的全局序列水位，因此没有较早事务较晚提交而被水位跳过的问题。通知丢失、跨进程写入及 API 重启通过下一轮补漏或重连恢复。

### 唤醒与有界资源

`_publish`、发令牌／轮换及撤销在事务中标记变动；`Repository.db` 只有在成功提交并释放连接后发出本进程提示。回滚和只读事务不唤醒，不增加 SQL。线程间提示先合并再投递 event loop，扫描之间保留 50 ms 间隔，避免提示风暴；无通知时约每秒补漏一次。实际撤销发现时间还包括连接池获取和 SQL 执行时间，沿用现有超时预算，不承诺数据库阻塞时仍能在一秒内送达。

每条连接独立接收 ping 和发送更新；每次最多取 8 条 outbox，达到一页后继续补齐。保留每次发送 3 秒超时、15 秒心跳和每秒最多读取一条应用 ping 的节流；Uvicorn 入站队列仍为 2。慢消费者不阻塞全局扫描或其他消费者；游标只在成功发送后前移。积压超过 outbox 保留范围时返回 `RESYNC_REQUIRED`，客户端重新取得快照。完整发送字节／回放预算留到 P6-E。

API lifespan 启动和停止 Hub，退出时清除订阅并解除提交回调；Hub 不新增常驻数据库连接。当前部署仍为单 API 实例；其他写进程只能由周期补漏发现，不声称已实现多副本跨进程实时通知。

### 开关与验证方法

默认 `PTCG_ONLINE_V2_STREAM_HUB_ENABLED=1`，Compose 使用 `PTCG_V2_STREAM_HUB_ENABLED`。仅接受 `0/1`；设为 `0` 并重启本次独立部署，即恢复原来的每连接每秒轮询。两种模式使用相同的持久游标、身份校验、错误和快照合同，无需变更数据库或回退数据。

新增用例覆盖成功提交才唤醒、回滚不唤醒、通知缺失补漏、他人游标拒绝、令牌与会话过期、撤销、成员隔离、数据库失败关闭、慢消费者隔离、生命周期清理以及轮询回退。既有完整服务回归继续验证控制权、游标截断、真实自然终局、HTTPS/WSS、进程死亡、未知响应与私有回放。

固定空闲微基线使用同一场原创合成对局，分别注册 1／8／32 条订阅、执行 10 轮检查，对比相同游标的旧 `Matches.stream` 轮询。不发送网络数据、不计算规则、不模拟 32 个真人或 32 场独立活跃对局，因此不能作为容量验收。

P6-A 报告保留在提交时的原始源码摘要上；P6-B 报告关联该基线摘要，并绑定当前源码与本轮完整服务回归。门禁拒绝历史报告改摘要、当前报告过期或将 SQL 微基线宣称为实测容量。

## P6-C：按局队列、公平轮转与分层准入

基线提交 `3ca9ca0`；服务版本 `0.6.0.dev3`，数据库 migration、共享规则包与线上协议不变。当前仍是单 API、单规则执行通道，每次规则调用仍启动受限子进程；常驻 worker、代次隔离和冷热缓存留到 P6-D。

### 准入、排队和提交

1. HTTP 边界继续限制请求大小、在途数与持久速率。命令入队前使用当前令牌查成员和同用户持久回执；这一步不读取 recovery 或快照，也不锁住对局等待。已有同内容回执直接返回，不受计算队列满、计算进程暂不可用影响；同 ID 不同内容冲突。
2. 内存去重键为 `(matchId, authenticatedUserId, commandId)`，内容摘要包含完整命令与 controllerId。相同在途请求共用一次执行，不重复占据任务槽；不同内容立即返回 `IDEMPOTENCY_CONFLICT`。每个等待者先鉴权，返回结果前再次鉴权并读取自己的持久回执，不能靠另一个会话的成功结果绕过到期或撤销。
3. 每局采用 FIFO；每轮只取一个任务。正在执行的对局若又有排队任务，完成后回到就绪队列尾部，排在已就绪的其他局之后。排队只持有请求闭包和 Future，不占 SQL 连接或线程池工作线程，不预加载隐藏规则状态。
4. 真正轮到执行时，原 `Matches.command` 重新读取已提交基线并执行原有鉴权、控制权、版本和合法选项检查。计算后再复核，原子提交恢复记录、双方私有帧、回执和 outbox；队列不能替代数据库约束。
5. 认输、控制权接管和内部技术终止继续通过已有短事务及时处理，不等待慢规则计算。它们可能使正在执行或排队的命令失效，旧命令在执行／提交时得到原有错误，不产生第二次推进。

执行者使用最早进入的有效请求身份。若该会话后来撤销，合并请求会一起收到该次执行的失败；不会自动换身份重新计算。调用方可用原 commandId 查回执或重新提交，持久幂等规则继续有效。

### 单规则通道与公平范围

卡组校验、开局初始化、初始投影与重新探测规则进程同样进入该调度器，避免它们从旁路争抢单个 worker 的非阻塞锁。卡组任务按已认证用户分组，后台任务使用独立内部组；初始化和投影分别占一个轮转机会。后台任务未轮到就超时，不会先领取 SQL 初始化 lease 或消耗初始化重试次数。

公平性覆盖就绪且未过排队期限的任务，不是 CPU 抢占。单次规则子进程仍有原有 20 秒超时；它运行期间其他任务可因排队预算耗尽而得到可重试 503。当前只证明轮转顺序和资源有界，不声称已实现多 worker 吞吐、长局低延迟或冷恢复的带权调度。

### 默认预算与回退

服务变量前缀为 `PTCG_ONLINE_V2_`；Compose 对应 `PTCG_V2_`。

| 后缀 | 默认 | 有效范围／含义 |
| --- | --- | --- |
| COMMAND_QUEUE_ENABLED | 1 | 0/1；0 回到原直接调用路径 |
| COMMAND_QUEUE_TOTAL | 32 | 1–256；执行中与排队的不同任务总数 |
| COMMAND_QUEUE_PER_MATCH | 2 | 1–16；每组一条执行加一条排队起步 |
| COMMAND_QUEUE_PER_USER | 4 | 1–32；同用户跨对局及卡组任务合计 |
| COMMAND_QUEUE_WAITERS | 64 | 1–512；所有原请求与合并重试等待者合计 |
| COMMAND_QUEUE_DUPLICATES | 4 | 1–32；每个任务最多 4 个等待者，含原请求 |
| COMMAND_QUEUE_SECONDS | 2 秒 | 大于 0、不超过 10；只限制未执行的排队等待 |

后台组也计入全局预算。每组上限同样应用于某用户的卡组校验组；不同组的任务仍共用每用户上限。预算满或排队超时返回 `CAPACITY_EXCEEDED` / 503 / retryable=true。计时器在超时移除排队任务，执行前再次检查期限，避免事件循环繁忙导致迟到计时器放行。

所有等待者离开时，尚未执行的任务立即移除；已经执行的任务继续到成功提交或明确失败，不能因 HTTP 断连提前释放规则通道。关闭服务拒绝新任务、清除排队者，并等待当前有界操作退出；重启后通过持久回执和 outbox 恢复，不恢复内存队列。失败和完成均释放任务、用户和组计数。新增指标只记录固定名称的接收、合并、拒绝、排队耗时、过期和取消数量，不输出身份或命令内容。

设 `COMMAND_QUEUE_ENABLED=0` 并重启该独立部署可回退；不会关闭数据库鉴权、幂等和提交检查。`MAX_INFLIGHT` / Uvicorn 长连接准入仍沿用既有规则，拆分连接与 HTTP 预算留到 P6-E。
