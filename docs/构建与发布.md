# 桌面 App 与独立 API 的打包和交付

当前入口（2026-11-03）。`release/` 存放忽略提交的 App、ZIP、DMG、镜像和私有 kit。构建与验证输出不进入源码树，发布结果须对应本次候选。

这是维护者构建手册；最终用户安装见[使用手册](启动使用与跨系统迁移.md)。公开源码不附完整卡表/引擎，所有 `--assets` / `--rules` 输入必须来自有权使用且与当前源码配套的批准资源；不能指向真实用户 profile。每次选新的输出目录，工具拒绝覆盖候选。

## 1. 构建前准备

- 开发 Python 3.14+、Node/npm、锁定 Rust 和平台工具链；实际桌面运行时为各自 lock 文件固定的 Python 3.14.10。Windows 输入准备脚本要求该固定开发 Python。
- 根目录统一 `npm ci`（包含 Web workspace）；生产 GUI 使用根目录 `npm run product:build`，不以旧 `apps/web` 单包构建替代。
- Mac 的运行时来源/摘要见 `scripts/native/runtime-lock.json`；Windows 见 `runtime-windows-lock.json` / `windows-wheel-lock.json`。
- 当前 4 个产品 Python wheel 与锁定外部 wheel 是配套输入；原生壳、后台、规则、展示索引各自校验，不从其他工作树共享已构建源码模块。
- `resources/artwork/builtin-index.json` 只是精确元数据索引。打包器将其绑定到批准卡表的文件摘要和 engineId；不会读取用户卡图缓存，也不下载全库图片。

## 2. macOS arm64 App 与 ZIP

需要 macOS arm64、Xcode 构建工具与锁定 Rust 1.90.0。纯 Python parser wheel 是必填项。使用 `scripts/native/prepare_windows.py` 可准备锁定源码和纯 Python wheel（同样可在 Mac 开发机运行）；源文件 SHA-256、`WITH_EXTENSION=0`、`SOURCE_DATE_EPOCH` 和构建工具版本均见 `scripts/native/windows-wheel-lock.json`，不要使用默认带扩展的 wheel 替代。

```sh
python3 -B scripts/packaging/macos.py \
  --runtime /approved/python-macos-arm64.tar.gz \
  --assets /approved/product-assets \
  --parser-wheel /approved/wheels/mwparserfromhell-0.7.2-py3-none-any.whl \
  --build-mode release \
  --output release/my-candidate/macos-arm64
```

可选 `--rust-bin`、`--cargo-home`、`--target-dir` 指向专用工具链/缓存。脚本构建两种 GUI、组装 runtime/产品源码/批准资产、裁剪开发依赖、修正已识别的原生库打包问题、生成组件和 SPDX/许可清单、运行源码外后台探针、封印并审计 App，输出 App、ZIP 和审计报告。`release` 是优化构建模式，不等于正式签名发行。

检查新包：

```sh
python3 -B scripts/native/desktop_smoke.py \
  --app 'release/my-candidate/macos-arm64/PTCG Lab Preview.app' \
  --output var/my-candidate-native-checks
codesign --verify --deep --strict \
  'release/my-candidate/macos-arm64/PTCG Lab Preview.app'
```

原生 smoke 使用独立测试 profile；不应以真实用户资料目录代替夹具。Mac 声明最低 12.0，当前支持 Apple Silicon；Intel Mac 暂不支持，最低系统无需实机测试，不能将免测记为通过。

### DMG 安装介质

先由安装工具读取 App 的 `bundleSha256`，它与 ZIP SHA-256、审计树摘要不同：

```sh
python3 -B -c 'from pathlib import Path; from scripts.product.desktop_install import bundle; print(bundle(Path("release/my-candidate/macos-arm64/PTCG Lab Preview.app"))["bundleSha256"])'
python3 -B scripts/packaging/c4_dmg.py \
  --app 'release/my-candidate/macos-arm64/PTCG Lab Preview.app' \
  --bundle-sha256 <上一步可信bundle摘要> \
  --output release/my-candidate/macos-dmg
```

将尖括号占位值替换为完整摘要再运行。介质含 `Install PTCG Lab.command`，执行受控备份/采用/版本切换；生成 DMG 不执行安装。本项目按开源源码交付，由用户自行编译，不要求 Developer ID、公证或 stapling。Mac 必需的本地 ad-hoc 代码封印及其严格验证仍保留，不能将其称作分发签名。

## 3. Windows x64 payload 与完整程序

准备固定输入（联网发生在开发准备阶段），然后构建当前 4 个产品 wheel：

```sh
python3 -B scripts/native/prepare_windows.py --output var/windows-inputs
python3 -m pip wheel --no-deps --wheel-dir var/windows-internal \
  packages/battle-protocol packages/engine-provider packages/online-client apps/desktop-api
npm run product:build
python3 -B scripts/native/windows_payload.py \
  --runtime var/windows-inputs/python-windows.tar.gz \
  --wheelhouse var/windows-inputs/wheels --internal var/windows-internal \
  --assets /approved/product-assets --output var/windows-payload
```

payload 是后台与资源准备结果，本身不是完整 App。原生 Windows 推荐使用非管理员完整自动化入口，覆盖真实 SDK、随包解释器、DPAPI/ACL/锁/IPC/Job Object 与 WebView2：

```powershell
python -B scripts/native/windows_pipeline.py --assets C:\approved\product-assets --output release\windows-native-run
```

完整前提及结果合同见 [Windows 手顺](Windows验证步骤.md)。已有批准 payload 的 Windows 原生 builder 为 `scripts/packaging/windows.py --payload ... --output ...`；其原生探针必须实际通过。

### 在 Mac 上交叉生成 Windows 候选

当前已使用 `d_windows.py` 生成实际 AMD64/MSVC GUI EXE 和完整便携 ZIP。需要固定 cargo-xwin 0.23.1、Rust 1.90.0、LLVM/LLD 和已批准 CRT/SDK 缓存；这些是开发输入，不放入最终程序。`--llvm-env` JSON 要提供工具目录 `bin`、`lld` 和 `DYLD_LIBRARY_PATH`，按批准工具链准备，不能引用另一台机器的绝对路径。

```sh
python3 -B scripts/packaging/d_windows.py \
  --payload var/windows-payload --output release/my-candidate/windows-x64/bundle \
  --rust-bin /approved/rust/bin --cargo-home /approved/cargo \
  --llvm-env /approved/llvm-env.json --cargo-xwin /approved/tools/cargo-xwin \
  --cache var/xwin-cache --target var/windows-target
```

输出包括 `bundle/PTCG Lab Preview.exe`、`bundle/backend/`、配置/身份助手、`Verify.ps1`、`BUILD.json`/`FILES.json`，ZIP 位于父目录 `windows-x64/PTCG-Lab-Windows-x64-preview.zip`。必须整包解压，不能只发送 EXE。PE 和哈希通过仅证明交叉制品，不等于 Windows 实机；交付时附 [Windows 验收步骤](Windows验证步骤.md)。用户已确认原生 Windows 和升级安装人工测试通过；该反馈不改写历史交叉编译/失败脚本记录。NSIS 是可选安装器，不作为开源源码交付门禁，不能将其与便携 ZIP 混用。

## 4. 图标与卡图资源

在线图库可单独构建和发布，完整操作见 [Cloudflare 卡图 CDN](Cloudflare卡图CDN部署.md)。维护端使用 Git 固定提交和原始图片字节，工具独立锁定 Wrangler；构建不登录或部署，发布必须显式提供候选摘要与账号。无需重新打包 App，也不更新 API 镜像。

当前图标为紫色/洋红/白色的三张大师球牌背扇形展开版，后两张图案弱化。源图及生成资源位于 `apps/native-shell/src-tauri/icons/`；启动页使用对应 PNG。

```sh
python3 -B scripts/native/icons.py
python3 -B scripts/native/icons.py --verify-app '/absolute/PTCG Lab Preview.app' --verify-exe '/absolute/PTCG Lab Preview.exe'
```

ICNS 最高 1024 像素，ICO 含 16/24/32/48/64/256 六尺寸；检查实际 App/EXE 内嵌字节，变更图标后需重新构建及封印。

卡图仅使用在线缓存或指定本地克隆目录，不再提供 ZIP 导入或单张上传。更新轻量索引见 [卡图设置](按需卡图与本地缓存.md#固定图片索引)。规则发布与完整 App 独立校验，克隆卡图不会更新规则或替代安装器。

## 5. 独立 API Server Docker Compose kit

Docker/Compose 和 OpenSSL 是打包机工具。例示地址需要替换为客户端实际可达且证书覆盖的局域网 IP/DNS：

```sh
python3 -B scripts/packaging/api_server.py \
  --rules /approved/rule-bundle --rule-pin <bundle.json的SHA256> \
  --host 192.0.2.10 --bind 0.0.0.0 --port 8876 \
  --platform linux/arm64 --output release/my-api-kit
```

默认构建当前源码的 API 基础镜像；显式 `--base-image` 只接受与当前 4 个服务 Python 包源码一致的已核验镜像。规则目录按 manifest/pin 验证，仅包含批准组件；规则身份在最终镜像内计算并实际激活，不借用宿主解释器身份。

kit 包含 API 和 PostgreSQL 镜像归档、Compose、独立项目/数据库秘密、测试 CA/TLS、管理器和客户端配置助手。架构支持输入 `linux/arm64` 或 `linux/amd64`，实际只对已测试架构声明通过。`--postgres-image` 可固定批准的 PostgreSQL 17 摘要。

默认 origin/绑定只在 localhost；局域网需显式地址及 `--bind`，实际防火墙、路由和证书也应匹配。已有保留端口含 8874，不能使用它替代当前测试服务。构建新 kit 不执行部署：

```sh
cd release/my-api-kit
python3 manage.py verify
python3 manage.py up
python3 manage.py check
python3 manage.py status
python3 manage.py down
```

管理器需要 Python 3.11+ 与 Docker Compose v2。仅操作本 manifest 的项目；加载核验镜像、启动独立数据库、执行 migration 后才启动 HTTPS API，readiness 为 `/readyz`。`down` 保留数据卷，不执行全局 prune。API 无 GUI、卡图、收藏或本地人机；App 连接步骤见[手册](启动使用与跨系统迁移.md#网络对战)。

kit 含 TLS 私钥、数据库密码等私有信息，不公开整个目录；客户端只使用经批准的公开连接信息/CA。测试证书有效期 30 天，公网使用 `--tls-mode acme` 自动申请/续期，备份恢复与发布手顺见 [API 公网部署与自动证书](API公网部署与自动证书.md)。公网包不生成私有测试 CA，客户端使用系统信任。

## 6. 清单、测试与发布状态

每轮候选保留来源摘要、dirty 状态、平台、规则/目录身份、文件哈希、ZIP/DMG 摘要及实际执行的检查。不能用上轮报告替换当前摘要，也不能因“可运行”而标记全部发布验收通过。


## 开源分发与可选签名

桌面由各自用户从开源源码编译，项目不要求维护者进行 Developer ID、公证或 Authenticode 签名。macOS arm64、Windows x64 和升级安装已获用户人工确认；Intel Mac 暂不支持，最低系统仅保留声明。已有签名工具继续作为可选维护工具，未签名本身不阻塞当前 API 交付。Mac 的本地 ad-hoc 封印和完整性核对仍是可运行包要求。

iOS 采用 TestFlight 有限发布，开发签名实机验收不等于已上传。正式团队签名、归档上传、App Store Connect 和许可/隐私材料另行准备，不作为继续 API 阶段的前置。详见 [iOS 手册](iOS开发与验收.md)。

macOS Developer ID 签名使用 `scripts/packaging/c4_signing.py --help`，要求显式当前 App 树摘要、证书身份和 team；公证与 stapling 使用 `c4_notary.py --help` 和 Keychain profile。Windows NSIS/签名入口为 `c4_windows.py --help`，须在原生 Windows 执行。工具中的签名或证书检查不能以关闭系统保护代替。选择这些可选分发途径时，必须真实核验对应证书、时间戳/公证与最终包，不把本地 ad-hoc 封印改称为已公证。

`scripts/packaging/source_identity.py` 绑定当前允许发布的源码，不读取历史阶段验收报告。整理源码不会重建已有二进制；每次分发应由当前 main 重新构建，并生成同批哈希与验证记录。
